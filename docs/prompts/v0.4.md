# Build prompt: `vkmin` v0.4 — what games need

Paste this to the coding agent. It assumes v0.3 is complete: resources are numbers, the journal
records and replays, the examples are the tests. `CLAUDE.md` still governs.

---

## The brief

v0.4 makes `vkmin` sufficient for someone to build a game on. Not a game engine — the API stays
a rendering and platform layer with no scene graph, no entity system, no physics, no audio — but
the set of primitives that a first-person shooter, a real-time strategy game, a top-down game,
a platformer, and a cel-shaded anime-styled game all turn out to need, provided in a form that
composes rather than in a module per genre.

The discipline is: one engine, five example games, and every primitive must be used by at least
two of them or it does not go in. Proof is a golden image per example under lavapipe, and a
journal per example that replays to identical pixels.

## What the genres have in common

Write this down before writing code, because it is what keeps the feature list short.

A shooter wants a perspective camera, many lights, real shadows, skinned characters, particles,
and a HUD. A strategy game wants a tilted camera over a large flat world, hundreds or thousands
of units, mouse picking, selection rectangles, health bars, and terrain. A top-down game wants an
orthographic camera, sprites mixed with 3D props, and picking. A platformer wants a side-on
camera, parallax layers, and one well-animated character. The anime-styled game wants any of the
above cameras, a quantised lighting model, outlines, and colour grading.

Stripped of the genre words, that is: cameras as maths; instancing at scale with GPU culling; a
sprite and quad batcher that serves particles, billboards, UI and parallax alike; skinning; a
shadow atlas; a lighting library the user's own shaders call into; an ID buffer for picking; a
heightfield mesh generator; and a small post-processing stack. Nine things. Nothing genre-shaped.

## The primitives

**Cameras are pure functions.** `vkmin_math.h` gains `perspective`, `orthographic`, `look_at`,
and a handful of constructors — `camera_fps(pos, yaw, pitch)`, `camera_rts(target, distance,
tilt)`, `camera_ortho_topdown(centre, extent)`, `camera_side(centre, half_height)` — each
returning a view and projection pair by value. There is no camera object, no camera state in the
context, and nothing to update. Also `ray_from_pixel(view, proj, px, py)` and ray-AABB and
ray-triangle intersections, pure, so game code can do its own coarse picking and collision
without the library growing a physics opinion.

**Instancing and GPU culling.** An instance buffer of `{ transform, prev_transform, mesh,
material, bounds, id }` in a storage buffer, a compute cull writing `VkDrawIndexedIndirectCommand`
records and a count, and one `vkCmdDrawIndexedIndirectCount` for the whole opaque set. The
strategy example requires this; the shooter benefits from it. Under lavapipe, provide a CPU-side
cull as the reference implementation behind a cvar, and require both to produce identical
draw lists in `make test` — an ordering-stable comparison, since the GPU version may emit records
in a different order.

**Sprites, particles, billboards and UI are one thing.** A quad batcher: an array of
`{ position, size, rotation, uv rect, colour, texture index, flags }` in a storage buffer,
rendered as instanced quads in one draw. A flag selects world-space billboard, world-space
flat, or screen-space. Particles are quads whose positions come from game code. Selection
rectangles, health bars, parallax backgrounds and the HUD are all this. The text renderer from
v0.1 is rewritten on top of it and gains a signed-distance-field font so it scales.

**Skinning.** Bone matrices in a storage buffer indexed by instance, applied in the vertex
shader on both the depth and forward passes. Compute pre-skinning remains the noted parallel
implementation for when the timings justify it.

**The shadow atlas.** One depth atlas; sun cascades in one quadrant; spot and point lights
allocated tiles by a simple screen-importance heuristic. Depth-only pipeline reusing the indirect
draw path. A cvar visualises the atlas and another colours the scene by cascade index.

**The lighting library is GLSL the user includes.** Rather than a `.shading = PBR | CEL |
UNLIT` enum on the pipeline, ship `shaders/lib/` with functions the user's fragment shader calls:
`lights_for_pixel()` returning the clustered light list, `shadow_sample()`, `pbr()`, `cel()`, and
`fog()`. The user writes their own fragment shader and composes these. Three canonical shaders
are provided as examples and are what the example games use. This is the developer-friendly
version: the library gives you the hard parts and does not tell you what your game looks like.

`cel()` specifically: N·L quantised through a small ramp texture the user supplies, a shadow
colour that tints rather than darkens, an optional rim term, and specular either off or reduced
to a single stepped highlight. That is the whole of the anime lighting model and it is about
thirty lines.

**Clustered lighting** stays as specified in the v0.1 architecture document. The shooter needs
it; the others run with a light count of one and pay nothing.

**The ID buffer.** Every opaque draw also writes its instance `id` to an `R32_UINT` attachment,
unconditionally — the execute-then-inhibit shape. `vkmin_pick(ctx, px, py)` reads one pixel of it
back, using host image copy on the modern path, and returns the id or zero. That is mouse picking
for the strategy and top-down games in one function with no CPU geometry tests, and it is
pixel-exact for free. The same attachment feeds a debug view that colours the scene by id.

**Terrain.** `vkmin_heightfield(desc)` — a pure function from a heightmap image and a scale to
a mesh's vertices and indices, with a simple chunked layout so the GPU cull can reject chunks.
No LOD in v0.4. The strategy example draws a couple of square kilometres of it.

**Post-processing.** The depth prepass now also writes octahedral normals to an `RG16` target.
The post stack, each a full-screen pass behind a cvar and ordered fixedly: outline detection
from depth and normal discontinuities, written as a dark line over the colour target; a 3D
colour-grading LUT sampled after tonemap; then tonemap to the swapchain. The outline pass is the
anime game's silhouette; it is a screen-space edge detect rather than an inverted-hull second
draw, because it is one pass with no per-object state and it works on everything including
skinned characters and terrain. Inverted hull is the noted parallel implementation for anyone
who wants per-object width control.

**Assets.** Meshes, skins and animations through glTF via `cgltf`, single-header, MIT, in the
`stb` tradition. Textures through KTX2 with BCn and offline mipmaps, plus the PNG path for tests.
Do not write a glTF loader; wrap the one that exists.

## Input, and the journal becomes a demo file

The platform layer grows one function: `vkmin_input(ctx)` returns a plain struct — key state and
edges, mouse position and buttons, one gamepad — as a snapshot for this frame. It is read at one
point in `vkmin_frame_begin` and never anywhere else.

Because it is plain data read at one point, it is journalled with everything else. A recorded
journal now contains the player's inputs, and replaying it replays the game. This is the
lineage of Quake's demo files and of the 1998 `.plan` on journalling, and it is why every
example game must be deterministic: fixed-timestep simulation driven by tick count derived from
frame index, interpolated for rendering, no clock anywhere in game code either. Provide
`ticks_for_frame(frame, hz)` in the maths header as the pure helper for that.

A gameplay bug report is then a journal file and a frame number, reproducible by an agent, and
the golden images for the example games are taken from replayed journals rather than scripted
cameras.

## The five examples

Each under five hundred lines of its own code, each deterministic, each with a recorded journal
in `tests/journals/` and golden frames from its replay. They are the acceptance test for the
whole release.

**`10_shooter`** — first-person camera through a small interior level, a few dozen lights,
cascaded sun through windows, two skinned enemies on patrol paths, muzzle-flash and smoke
particles on fire, a HUD. The v0.1 corridor demo, made playable.

**`11_rts`** — tilted camera over heightfield terrain, two thousand instanced units in two
teams moving on deterministic paths, box-select via the sprite batcher, picking via the ID
buffer, health bars, one directional shadow. This is the example that proves the indirect path
and the cull.

**`12_topdown`** — orthographic camera, a tile-based floor as one mesh, sprites for characters
mixed with 3D props, picking, a single point light following the player.

**`13_platformer`** — side-on orthographic camera, three parallax layers through the batcher,
one skinned character with idle, run and jump, moving platforms as instances.

**`14_anime`** — the platformer's character and a small scene under the `cel()` shader, the
outline pass, a colour LUT, and a rim light, from an orbiting camera. Cel shading is unforgiving
of small lighting differences, which makes its golden images unusually good regression
detectors; that is a feature.

## Milestones

Each leaves all existing goldens identical and adds the new example's goldens.

1. Cameras, rays and `ticks_for_frame` in the maths header. `vkmin_input` and its journalling.
   Existing examples gain deterministic input replay. No rendering change.
2. Instancing, GPU cull with the CPU reference, `cgltf` and KTX2 loading. `11_rts` without
   terrain or picking.
3. The quad batcher and SDF text. `12_topdown` and `13_platformer` first passes.
4. Shadow atlas, clustered lights, skinning, the GLSL lighting library. `10_shooter`.
5. Heightfield and the ID buffer. `11_rts` complete.
6. Normal target, outline, LUT, `cel()`. `14_anime`.

## Acceptance and budget

Core under 7000 lines with both paths, which is honest for what is now a complete rendering
layer; the shader library under 1000; each example under 500. Every primitive used by at least
two examples — list the users of each in the final report, and remove anything with one. All
five journals replay to identical pixels on both paths under lavapipe at their `--profile=
lavapipe` settings. Validation silent everywhere. `make test` from clean with no GPU.

And the game developer's test: someone who has shipped a game reads `vkmin.h`, the shader
library, and one example matching their genre, and can say what they would build and what they
would have to add. Ask that person which primitive they missed. If more than one of the five
would miss the same thing, it belongs in v0.5.

Report what was run and what was believed.
